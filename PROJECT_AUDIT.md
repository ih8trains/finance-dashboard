# Полная диагностика финансового дашборда — 2026-11-13

## Итог

**Основная цепочка синхронизации впервые успешно прошла в реальном Chrome на v4.0.5.** Google Sheets больше не участвует в штатной синхронизации расширения, а дашборд уже читает месячные архивы GitHub и отдельный зашифрованный файл пользовательских данных.

Но проект пока нельзя считать полностью очищенным и готовым к удалению старых компонентов: в `index.html` остался рабочий интерфейс пересборки архивов через старый Google Apps Script, старый URL GAS и устаревшие подписи. Также расширение при каждом запуске переписывает архивы даже тогда, когда банковские данные фактически не изменились, и создаёт новые резервные копии. Перед удалением мусора нужно устранить эти остатки и определить политику резервирования.

## 1. Фактический результат реальной синхронизации

Пользователь подтвердил результат v4.0.5:

- Период: последние 30 дней.
- Получено: 303 операции.
- Добавлено: 0.
- Обновлено: 303.
- Некорректных: 0.
- Месяцев обновлено: 2.

Это подтверждает реальный проход по Т-Банку и GitHub: авторизация, чтение операций, чтение/расшифровка существующих архивов, резервирование, запись обновлённых файлов, проверка записи и обновление manifest.

Ограничение результата: счётчик `Обновлено` сейчас означает «операция уже существовала и была повторно получена», а не обязательно «в банковских полях реально изменилось значение». Поэтому 303 обновлённых не доказывают, что все 303 операции действительно изменились. Синхронизация также не проверяла в реальном аккаунте добавление совершенно новой операции: в этом запуске добавлено 0.

## 2. Проверка GitHub-хранилища

Проверено через GitHub Contents API и дерево репозитория:

- 25 месячных архивов: с 2024-11 по 2026-11.
- Суммарно по manifest: **6 830 операций**.
- Все 25 записей имеют статус `verified`.
- Для каждого из 25 файлов проверены JSON-структура envelope, месяц, количество строк, SHA-256 открытого содержимого из envelope, алгоритм AES-GCM, KDF PBKDF2-SHA-256 и 600 000 итераций.
- Для всех 25 архивов значения SHA-256 и count совпадают с manifest.
- Октябрь 2026 после синхронизации: 327 операций, метаданные совпадают.
- Ноябрь 2026 после синхронизации: 136 операций, метаданные совпадают.
- `data/user-data.json.enc` существует отдельно от банковских архивов. Синхронизация расширения не должна его изменять; в успешном кодовом сценарии он не затрагивается.

Проверка выше подтверждает целостность структуры и согласованность manifest с envelope. Она не является отдельной расшифровкой каждого архива этим аудитом: пароль пользователя не запрашивался и не использовался.

## 3. Резервные копии и лишние файлы

В текущем дереве GitHub:

- 26 файлов в `data/backups/`.
- Общий размер резервных файлов: 16 617 100 байт (около 15,85 MiB).
- 23 резервные копии относятся к первоначальной пересборке `rebuild-*`.
- 3 копии относятся к синхронизациям `sync-*`.
- 25 путей резервных копий указаны в поле `backupPath` manifest.
- Одна старая резервная копия октябрьского архива от неудачного запуска v4.0.2 не является текущей ссылкой `backupPath`, но остаётся в репозитории.

Резервные копии не используются при обычной загрузке дашборда и не нужны для чтения операций. Они нужны только для восстановления предыдущей версии архива. Удалять их можно после согласованного решения о резервировании и очистки ссылок `backupPath` в manifest.

**Важно о Git:** удаление backup-файлов из текущего дерева не удалит их из истории коммитов Git. Если цель — уменьшить размер всего репозитория и убрать старые версии файлов из истории, потребуется отдельная операция переписывания истории (filter-repo + force push). Это отдельный рискованный шаг; его нельзя смешивать с обычным удалением файлов.

## 4. Проверка расширения T-Bank Auto Sync v4.0.5

Проверено по фактическому ZIP v4.0.5:

- В архиве только 8 файлов расширения: manifest, popup HTML/JS, background JS и 4 иконки.
- `manifest.json` корректен, версия 4.0.5, Manifest V3.
- `background.js` и `popup.js` проходят `node --check`.
- Popup ссылается на существующий `popup.js`; ссылка на зеркало Т-Банка сохранена.
- Расширение запрашивает операции Т-Банка методом GET с `credentials: include`; записи в Т-Банк в коде синхронизации нет.
- Запись архивов выполняется через GitHub Contents API.
- Новые/обновлённые архивы и резервные копии перечитываются через Contents API, а не через Raw CDN.
- В успешном сценарии GitHub PAT и пароль архивов удаляются из `chrome.storage.local`; при ошибке остаются для повторного запуска.

### Найденная проблема логики синхронизации

В цикле обработки месяца каждая полученная операция с уже существующим ID увеличивает счётчик `updated`, даже если все банковские значения совпадают с сохранённой строкой. После этого код в любом случае:

1. заново шифрует весь месячный архив;
2. создаёт новую резервную копию;
3. записывает архив;
4. обновляет manifest.

Следствие: повторный запуск без фактических изменений всё равно создаёт новые версии архивов и backup-файлы. Это объясняет результат «303 обновлено» и приводит к бесконечному накоплению резервных копий.

**Нужно исправить до дальнейшей регулярной эксплуатации:** сравнивать нормализованную входящую строку с предыдущей; считать обновлением только реальные изменения банковских полей; если месяц не содержит новых или изменившихся строк — не перешифровывать его, не создавать backup и не менять manifest. Ручную колонку «Моя группа» при сравнении и обновлении сохранять.

### Дополнительные технические замечания

- Получение операций использует один запрос за 30 дней и ожидает массив в `data.payload`. Пагинация отдельно не реализована; при росте объёма нужно проверить, что банк не ограничивает размер ответа.
- Состояние `running` хранится только в памяти service worker. Для обычного сценария работает, но защита от двух одновременных запусков между перезапусками worker не является устойчивой блокировкой.
- Текущий алгоритм последовательно обрабатывает месяцы и обновляет manifest после каждого месяца. Это позволяет восстановить уже завершённые месяцы, но при сбое посередине возможна частично завершённая синхронизация. Нужен явный отчёт по завершённым месяцам и безопасное продолжение.
- PAT и пароль временно хранятся в `chrome.storage.local` до успеха. Это локально в профиле Chrome, но не подходит для общего профиля/чужого компьютера.

## 5. Проверка дашборда index.html

Дашборд уже использует GitHub как источник банковских данных:

- Читает `data/manifest.json` и месячные архивы.
- Расшифровывает AES-GCM / PBKDF2-SHA-256.
- Читает пользовательскую разметку и настройки из `data/user-data.json.enc`.
- Сохраняет разметку и настройки обратно через GitHub Contents API.
- Ручная разметка хранится отдельно от банковских полей.
- Старые `custom_category` в разметке UI не использует; пользовательская категория не заменяет банковскую категорию, для пользовательской классификации используются теги и поля контекста.

### Найденные остатки Google Sheets / GAS

В `index.html` до сих пор есть:

- Старый `API_URL` на Google Apps Script.
- Функция `api()`, отправляющая запросы в GAS.
- Кнопка «Пересоздать все архивы», которая запускает `runArchiveRebuild()` и обращается к GAS за листами Google Sheets.
- Неиспользуемый старый код миграции пароля архивов через GAS.
- Кнопка «Создать и проверить архивы» без подключённого обработчика.
- Текстовые подписи о хранении настроек и тегов в Google Sheets.
- Текст в боковой панели, утверждающий, что разметка хранится локально, хотя теперь она сохраняется в GitHub.

Это не часть нового штатного потока, но это не просто косметический мусор: старая кнопка пересборки всё ещё активна и может обратиться к старому GAS. Её нужно удалить вместе с устаревшим API_URL, `api()`, старой миграцией и архивными обработчиками после проверки, что других активных вызовов GAS не осталось.

### Риск кеширования при входе

Манифест дашборд загружает с `cache: no-store`, но сами месячные архивы запрашивает без такого режима и без cache-busting параметра. После обновления архива Raw CDN потенциально может отдать старую копию, тогда как свежий manifest уже содержит новые метаданные. Это тот же класс проблемы, который ранее ломал проверку в расширении.

До удаления старой инфраструктуры следует добавить `cache: no-store` и cache-busting для каждого запроса месячного архива.

### Производительность входа

Все месяцы скачиваются и расшифровываются через `Promise.all`. Это ускоряет сетевую часть, но одновременно запускает 25 derivation PBKDF2 по 600 000 итераций. На слабом устройстве это может создавать пиковую нагрузку. При необходимости ограничить параллелизм небольшими пакетами и измерить фактическое время входа.

## 6. Старый Code.gs

`Code.gs` остаётся в корне репозитория. В нём сохранены старые обработчики синхронизации Google Sheets, разметки, настроек и пересборки архивов. В текущей копии репозитория `SECRET_PASS` пустой. Это не доказывает состояние уже развёрнутого Apps Script, но подтверждает, что GAS-код и его URL больше не нужны для штатного потока.

После удаления всех GAS-вызовов из `index.html` файл `Code.gs` можно удалить из активной ветки. Сам опубликованный Apps Script и таблицу отдельно отключать/удалять только после финального подтверждения, что ни одна версия дашборда или расширения к ним не обращается.

## 7. Что можно и нельзя удалять

**Оставить обязательно:**

- `data/YYYY-MM.json.enc` — 25 основных месячных архивов. Это единственное текущее хранилище банковских операций для дашборда. Удаление приведёт к потере истории в интерфейсе.
- `data/manifest.json` — индекс и контрольные метаданные архивов.
- `data/user-data.json.enc` — ручная разметка, комментарии, теги, правила, бюджеты и настройки.
- `index.html` — сам дашборд.

**Кандидаты на очистку после исправлений:**

- 26 файлов/каталогов в `data/backups/` — после определения минимальной политики восстановления и очистки `backupPath`.
- `Code.gs` и GAS-совместимый код/кнопки из `index.html`.
- Мёртвые функции миграции/пересборки архивов, старые подписи Google Sheets и локального хранения.
- Старые версии ZIP расширения и временные файлы в пользовательской рабочей папке — они не находятся в репозитории и на GitHub не влияют.

## 8. Рекомендуемый порядок завершения очистки

1. Исправить расширение: diff банковских строк; не трогать месяцы без реальных изменений; backup только перед фактической записью; понятное продолжение после частичного сбоя.
2. Исправить дашборд: cache-busting для архивов; удалить GAS URL, функцию `api()`, кнопку и функции старой пересборки; обновить устаревшие подписи.
3. Проверить сохранение/повторную загрузку пользовательской разметки и настроек, затем провести ещё одну синхронизацию без изменений: ожидаемый результат — 303 получено, 0 добавлено, 0 реально изменено, 0 новых backup, месяцы не переписываются.
4. Проверить сценарий с одной новой операцией и сценарий с изменившимся банковским полем на тестовой ветке/копии.
5. После этого удалить `Code.gs` из активной ветки и очистить backup-файлы, обновив manifest. Не переписывать историю Git без отдельного решения.
6. Только после повторной проверки Pages, пользовательских данных и синхронизации отключать/удалять Apps Script и Google Sheets.

## Итоговое решение

**Данные целы по структурным проверкам, реальная синхронизация v4.0.5 прошла. Но очистку пока не выполнять:** сначала нужно устранить избыточные перезаписи/backup, остатки GAS в дашборде и кеширование архивов. Основные 25 месячных архивов удалять нельзя — это действующее хранилище операций.
